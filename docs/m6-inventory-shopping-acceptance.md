# M6-A2 库存与采购闭环验收

## 已交付

- 家庭库存可选择关联菜谱中的食材；自由名称库存和日用品库存继续兼容。
- 同一家庭、同一食材和同一单位只允许一条关联库存，服务端同时校验食材的家庭归属。
- 菜单采购清单按 `菜单需求 - 可用库存 = 建议采购` 重新生成，只有建议数量大于零时才创建自动采购项。
- 自动采购项保存菜单需求、生成时库存和建议采购三项快照，界面直接展示计算明细。
- 采购清单重建继续保留同食材、同单位项目的已勾选状态，并保持事务回滚保护。
- 新增不可变库存流水，覆盖入库、消耗、调整和撤销；所有数量变化均记录变化前后快照、变化量、单位、操作者、来源与时间。
- 购物项由用户查看预计变化并明确确认后入库；菜单结束仍只锁定菜单，必须再次查看逐项预计扣减并确认扣库。
- 最近的购物入库或整餐扣库可以撤销。撤销追加整组反向流水，不更新或删除原流水。

## 计算边界

- 只有 `accepted` 或 `cooking` 的菜单菜品参与采购计算，食材数量来自点菜时保存的做法快照；旧菜单没有快照时回退到菜品食材。
- 库存必须同时匹配家庭、`ingredientId` 和单位才可抵扣。同名自由库存、其他单位或其他家庭的库存都不参与。
- 库存足够时不生成采购项；库存为零或没有关联库存时，普通食材按全部需求采购。
- 常备食材已关联库存时按实际余量计算；尚未关联时继续跳过，避免升级后突然产生大量调料采购项。
- 自动采购项记录的是生成时快照。库存变化后需要重新生成清单，已有清单不会被后台静默改写。

## API 与数据

```text
GET   /inventory
POST  /inventory-items
PATCH /inventory-items/:id
POST  /shopping-list/generate
GET   /shopping-list?date=YYYY-MM-DD
GET   /shopping-items/:id/inventory-preview
POST  /shopping-items/:id/confirm-stock
GET   /menus/:id/inventory-preview
POST  /menus/:id/confirm-consumption
GET   /inventory-transactions
POST  /inventory-transactions/:id/reverse
```

- `inventory_items.ingredientId` 是可空食材引用。
- `shopping_items.requiredQty`、`availableQty` 和 `totalQty` 分别保存需求、可用库存和建议采购数量。
- 旧库存和手动购物项的新字段均为空，不需要数据回填。
- `inventory_transactions` 保存 `householdId`、`inventoryItemId`、`operationId`、`type`、`quantityBefore`、`delta`、`quantityAfter`、`unit`、`actorId/actorName`、`sourceType/sourceId`、`idempotencyKey`、可选 `reversesTransactionId` 与 `createdAt`。
- 家庭和幂等键组合唯一；变化前后数量必须非负且满足 `quantityAfter = quantityBefore + delta`。数据库触发器拒绝任何流水 `UPDATE` 或 `DELETE`。
- 迁移历史已按序推进到 `1785229400000-add-inventory-transactions`；`synchronize` 继续保持 `false`。

## 确认与撤销边界

- 购物项必须先勾选为已买，并有大于零的数量。关联食材和单位能够唯一匹配库存时自动选择；自由名称项必须由用户选择同单位库存项，也可以暂不入库。
- 已关联食材的购物项不能选择其他食材库存；其他家庭库存项按不存在处理。重复点击或并发重试返回原入库流水，不再次增加数量。
- 重建购物清单会保留已确认来源的原始数量和状态；同一食材之后出现新的采购差额时另建待确认项，不覆盖已入库历史。
- 菜单必须先完成并锁定。扣库按做法快照聚合食材和单位，旧菜单回退菜品食材；没有对应库存的食材明确显示为跳过。
- 同一食材已有其他单位库存时视为单位不匹配，匹配库存不足时视为库存不足，两者都会阻止整餐扣库，不产生部分流水。
- 整餐扣库共享一个 `operationId` 并在一个数据库事务中提交。并发确认只产生一组流水。
- 只有仍是相关库存项最近动作、且尚未撤销的入库或扣库可以撤销。菜单扣库按整个操作组恢复；重复撤销返回已有反向流水。
- 已有流水的库存项和已入库购物项不能删除，避免历史来源失真。

## 前端验收

- 购物清单的已勾选项提供鼠标和触控可用的“入库”按钮；弹窗展示目标库存、当前数量、采购数量和预计结果。
- 自由名称购物项在弹窗内用可点击列表选择库存项；没有合适库存时提供明确的“暂不入库”操作。
- 菜单完成后显示独立“确认扣库”按钮；预计扣减、缺少库存、单位不匹配和库存不足逐项展示，不与“结束本餐”合并。
- 购物项持续显示“已入库”或“入库已撤销”，菜单持续显示“已确认扣库”或“扣库已撤销”。
- 家庭库存页展示最近流水、操作者和变化前后数量；仅可撤销的最近入库/扣库显示触控按钮，并在二次确认中展示预计恢复数量。
- 所有核心操作提供加载、成功、失败、重复确认和已撤销状态，不依赖键盘快捷键。

## 自动验收

- 有库存时正确计算差额，库存足够时不生成采购项。
- 单位不同和其他家庭的库存不会错误抵扣。
- 已关联常备食材参与计算，未关联常备食材保持兼容跳过。
- 重建清单保留勾选状态；库存数量变化后使用最新余量。
- 重复食材单位和跨家庭食材关联分别返回 409 与 404。
- 原有数值溢出用例继续验证事务失败后旧清单完整保留。
- Expo Web 回归覆盖用鼠标打开库存编辑器、搜索并选择菜谱食材。
- 购物入库预览验证 `2 -> 5`，并发双击验证只产生一条入库流水和一次数量变化。
- 已确认入库后新增菜单需求会生成新的待确认差额项，不复用或改写已确认来源。
- 自由名称验证未选库存、单位不匹配和跨家庭库存分别被拒绝。
- 菜单扣库验证单位不匹配、库存不足、缺少库存跳过、三项整组扣减和并发幂等。
- 撤销验证较早流水不可撤销、整餐反向恢复、并发重复撤销，以及撤销后重复确认不再次扣库。
- 数量调整验证客户端幂等键并发只写一条调整流水；数据库直接 `UPDATE/DELETE` 流水均被触发器拒绝。
- 完整 API 回归同时演练全新数据库与旧结构升级，并执行实体结构漂移检查。

## 后续边界

本批不做单位自动换算，也不根据菜名猜测自由购物项对应的库存。已撤销的同一来源不会再次确认；若确需重新发生，应建立新的购物项或新的菜单来源。家庭资产和积分继续使用各自独立流水，不复用库存流水表达其他业务。
