## 0. 问题与一句话方案

**现在的问题**：`smart_home_devices` 一行是一个 HA **实体**。King 挑一台洗衣机，页面上就是「洗衣机 运行状态」「洗衣机 剩余时间」「洗衣机 程序」几行平铺，
按钮全摆在行里（空调一行最多七个按钮），没有「这是一台什么设备、现在怎样、最该按哪个」的主次。

**方案**：白名单从「实体」改成「设备」。一台设备 = 一个**主实体**（决定卡片的状态句和唯一主按钮）+ 至多 4 个**次要实体**（只在详情里当信息 chips）。
页面按「场景 → 房间 → 设备卡」三层摆；卡片只有图标、名字、一句状态、至多一个主按钮；其余全部进详情 sheet。

## 1. 三个参考：只取信息层级

调研于 2026-09-29，WebSearch + WebFetch。抓不到的如实标出，没有据此下结论。

### 1.1 米家 App（资料最弱）

来源：新浪众测两篇评测、新浪科技、极客公园、虎嗅（后者只有要点）。知乎专栏、IT 之家两篇 403 没抓到。

1. 7.0 起首页叫「全屋」，**按功能模块**而不是按房间分块：音箱 / 扫地机卡片在上，快捷场景（最多 4 个）其次，再往下是灯光、环境、摄像机、窗帘。
2. 设备卡片带房间名、设备名、在线状态和一个开关；灯光模块有「全开 / 全关」，多键开关可以拆成多张卡。
3. 某个模块没有对应设备时整块不显示，不留空壳；11 版另起「场景」页，按安防 / 环境 / 照明 / 遮阳四类放。

**没能证实**：顶部房间 tab、长按进详情、离线卡片怎么灰显，这三条都没找到来源（只确认列表会写「设备离线」，8.3 版加了离线原因分析）。
所以下面的设计**没有**把这几条当米家的做法来引用。

### 1.2 Home Assistant Mushroom 卡片

来源：`piitaya/lovelace-mushroom` 的 README 与 `docs/cards/` 下 entity、light、vacuum、cover、climate、chips、template 七篇。

1. 一张卡压成一行：**图标（开着时着色）+ primary_info（默认名字）+ secondary_info（默认状态）**，两个 info 都可以换成名字、状态、上次变化时间或留空。
2. 滑杆和按钮这类控件**默认关闭、按需打开**；`collapsible_controls` 能在设备关着时把控件收起。
3. 点卡片的默认动作**按类型分**：灯、窗帘、空调点一下就切换，扫地机和通用实体点一下弹详情；长按、双击一律弹详情。顶部可以放一排 chips 做摘要。

### 1.3 Apple 家庭 App（iOS 16 重设计后）

来源：9to5Mac、MacStories、AppleInsider、MacRumors 的 iOS 16 评测，support.apple.com 102056。控制配件那篇官方指南只抓到目录。

1. 最上面一排**分类状态按钮**（灯、气候、安全、音箱、水），按钮上直接写摘要（例：「3 盏灯开着」），往下依次是摄像头、场景、收藏，再往下每个房间一个分区。
2. 磁贴靠**颜色和形状**表达开 / 关；**点左侧圆形图标 = 开关，点磁贴其余地方 = 详细控制**，长按进入编辑。
3. 连不上的配件标「无响应」；分区顺序和磁贴大小可以调。有评测批评旧版磁贴长得太一样，不好区分，也浪费空间。

### 1.4 取了什么、没取什么

| 取 | 来自 | 落在哪 |
| --- | --- | --- |
| 场景放最上面一排 | Apple、米家 | 第一层 |
| 按房间分区，而不是按类型铺 | Apple | 第二层（米家按功能模块分，家里设备少，按功能分反而零碎，不取） |
| 状态靠颜色、卡片只有一句状态 | Mushroom、Apple | 设备卡 |
| **点「那个按钮」= 执行，点卡片其余地方 = 详情** | Apple 的点击区拆分 | 设备卡 |
| 按类型决定有没有主动作（只读设备整卡都是详情入口） | Mushroom 按类型给默认动作 | 主按钮表（§3.3） |
| 控件默认不摆，要细调进详情 | Mushroom 的控件默认关闭 | 空调的模式和温度只进详情 |
| 没有内容的区块整块不出现 | 米家 | 场景行、今天页区块 |
| 「无响应」要写出来 | Apple、米家 | 离线灰显 + 状态句「离线」 |
| **不取**：顶部分类摘要按钮（Apple）、顶部 chips（Mushroom） | — | 家里只有 6 台左右设备，摘要比设备本身还多，属于过度设计 |
| **不取**：长按编辑、磁贴大小可调 | — | 设置页已经承担编辑；家里人不需要排版能力 |

## 2. 信息层级（`/house/smart-home`）

```
标题「智能家居」· 一行小字：N 台设备 · 刚刚同步        [设置]（管理员）
[HA 断开横幅]（只在断开时）
第 1 层  场景一排（scene / script，横向滚动，一键执行）   ← 没有就整行不出现
第 2 层  房间分段（按白名单的房间）
         └ 设备卡网格：手机 2 列、桌面 4 列
第 3 层  点卡片 → 详情 sheet（手机底部上推、桌面居中）
```

### 2.1 设备卡：只放四样东西

| 位置 | 内容 | 说明 |
| --- | --- | --- |
| 左上 | 图标 | 按**图标类型**选（§4.1），**开 / 关 / 运行 / 离线用颜色表达**：松绿底 = 开着 / 运行中；平底 = 关着 / 待机；暖橙 = 要留意（暂停、出错、滤芯低、洗好了没人收）；半透明 = 离线 |
| 右上 | 主按钮（至多一个） | 有权限且此刻有意义时才出现。**按钮上写的是「按下会发生什么」**（暂停 / 关上 / 打开），不是当前状态 |
| 中 | 中文名 | 一行，超长截断 |
| 下 | 一句状态 | 人话，复用 `attention-copy` 的写法：「清扫中 · 62%」「充电中 87%」「剩 23 分钟」「烘好了」「已关」「离线」 |

没有第二个按钮。点主按钮直接执行（成功给一下轻触感，沿用 `navigator.vibrate(10)`）；**点卡片其余任何地方打开详情**。
只读设备（海尔洗衣机、净水器）整张卡都是详情入口。

无障碍：卡片不能是「按钮里套按钮」。实现上卡片是一个 `article`，里面一个铺满整卡的「打开详情」按钮垫底、主按钮叠在上层，两个都有各自的 `aria-label`。

### 2.2 排序

- 房间：按设置页里的房间顺序；没填房间的归「其他」放最后。
- 房间内：`sortOrder`；**离线设备排到本房间末尾**。
- 「在今天页显示」的设备在这一页**不单独置顶、不重复出现**，只在自己房间里正常排。

### 2.3 详情 sheet

从上到下：

1. **是谁**：图标、名字、房间 · 厂商型号（来自 HA 设备注册表）。
2. **现在怎样**：状态句 + 一句补充（「10:12 开始，已经扫了 18 分钟」；空调写「按上次操作显示」，沿用现有 `assumed`）。
3. **能做什么**：主实体的**全部动作**，按钮位置固定；此刻说不通的**置灰不隐藏**，免得按钮跳位。空调的开关、四种模式、设定温度 ±1 **只在这里**。没权限时换成一行「管理员还没开放控制」。只读设备写「这台只能看」及原因。
4. **更多信息**：次要实体 chips，最多 4 个（剩余时间、电量、滤芯寿命、主刷寿命……）；到阈值的 chip 变暖橙，阈值沿用留意规则，不另起。
5. **最近操作**：审计表里这台设备的最近 3 条（谁 / 动作 / 时间 / 成败），联动触发的写清是哪条联动。
6. **管理员**：「在今天页显示」开关；一个「改名字、房间、主 / 次实体 ›」链接跳设置页并展开这一行。

手机：底部上推，下拉可关，进入用 ease-out（iOS 那条 `cubic-bezier(0.32, 0.72, 0, 1)`，与 `index.css` 的 pop-in 同一条），`prefers-reduced-motion` 时不动。
桌面：同一内容居中弹出，宽 440，Esc 和点遮罩关闭。

### 2.4 断开与离线

| 情况 | 页面 |
| --- | --- |
| 某台设备离线（主实体 `unavailable`） | 卡片半透明、状态句「离线」、不出主按钮、排到本房间末尾；详情照常能开（看上次的次要信息和操作记录） |
| **整个 HA 断开** | 顶部一条横幅「连不上 Home Assistant，下面是 10:32 的状态，暂时按不了。家里其他功能不受影响。」；**卡片保留上次状态、整体灰显、收起主按钮**；场景行不出现 |
| API 重启后 HA 仍断开（内存里没有上次状态） | 卡片状态句「—」，其余同上 |
| 没连 HA / 白名单为空 | 沿用现在的空状态（管理员给去设置的链接，成员写「等管理员连好」） |

### 2.5 今天页「家里的设备」区块（E5 用同一套组件）

- 位置按 pre-trial-plan H3 的修正：「今天吃什么」之后、「今日待办」之前；桌面在主列同一位置。
- 内容：`pinnedToToday` 的设备，**最多 4 张**（两行），超出按排序取前 4，标题右边「全部 N 台 ›」。
- 卡片与详情就是设备页那个组件，一模一样；点卡片在今天页原地打开详情，不跳页。
- 没有置顶设备时整个区块不出现。HA 断开时同设备页（上次状态灰显），区块内一行说明，不另起横幅。
- **分工**：设备卡是「操作」，留意卡是「待办」。滤芯低、烘完两小时没人收、HA 离线超过一小时——这些走 E5 的留意规则，不靠一张「低于阈值才出现」的设备卡（见 §8 第 1 条）。

### 2.6 设置页

结构不变（连接 / 白名单 / 最近操作在左，目录在右；「联动」分段不变），只改两处：

- **目录**：「加进来」的对象从实体改为**设备**。每台设备的卡头一个「加进来」按钮；卡里给每个实体标「主」「次」徽标，预览加进来后的默认搭配。没有归属设备的实体（场景、脚本、helper）照旧一个一个加，各自成为「单实体设备」。
- **白名单表**：一台设备一行（图标、名字、房间、主实体一句状态）。行内「展开」后可改：中文名、房间、图标类型、主实体（单选，本设备的实体，可控类在前）、次要实体（多选至多 4 个，旁边显示当前值方便挑）、允许控制、谁能控、在今天页显示。

## 3. 状态句与主按钮

### 3.1 状态句（按图标类型）

| 图标类型 | 例句 | 取值 |
| --- | --- | --- |
| 扫地机 | 清扫中 · 62% / 充电中 87% / 在充电座上 / 回充中 / 暂停了（暖橙）/ 出错了（暖橙） | 主实体 vacuum 的状态 + `battery` |
| 窗帘 | 开着 / 开了 40% / 关着 / 正在打开 | cover 状态 + `position` |
| 空调 | 已关 / 制冷 26° / 送风（后缀「≈」表示按上次操作显示） | climate 状态 + 设定温度 |
| 洗衣机 / 烘干机 | 剩 23 分钟 / 洗好了 · 烘好了（暖橙）/ 空闲 | 主实体（运行状态）；运行中时若有「时长」类次要实体（单位 min / h），取它拼「剩 N 分钟」 |
| 净水器 | 滤芯剩 64% / 滤芯剩 8%（暖橙，低于联动里设的阈值） | 主实体（滤芯寿命传感器） |
| 开关 / 灯 / 风扇 | 开着 / 已关 | on / off |
| 其他传感器 | 27.5° / 58% / 3 分钟 | 值 + 单位（沿用 `sensorLine`） |
| 任意 | 离线 / 不知道 | `unavailable` / `unknown` |

实现是 `smart-home-copy.ts` 里新增 `deviceStatusLine(device)`：以现有 `smartHomeStateLine` 为底，再按图标类型借一个次要实体补半句。

### 3.2 颜色

| 语义 | 条件 | token |
| --- | --- | --- |
| 运行 / 开着 | 清扫中、开着、制冷、洗涤中… | 卡底 `accent-soft`，图标块 `accent` |
| 关着 / 待机 | 关着、在充电座上、空闲 | 卡底 `surface`，图标块 `muted` |
| 要留意 | 暂停、出错、滤芯低、洗好了 | 图标块 `warm-soft` + `warm`，状态句 `warm` |
| 离线 / 断开 | `unavailable`、HA 断开 | 整卡降不透明度（断开时再去色） |

暗色下这几个 token 已有对应值（`html[data-theme='dark']`），不用另配。

### 3.3 主按钮（至多一个）

| 类型 | 此刻状态 → 按钮 | 动作 |
| --- | --- | --- |
| 扫地机 | 清扫中 / 回充中 → **暂停**；暂停了 → **继续**；在座上 / 待机 → **开始**；出错 → 无 | pause / start |
| 窗帘 | 关着 → **打开**；开着 / 开了一部分 → **关上**；正在动 → **停** | open / close / stop |
| 开关 | 开着 → **关掉**；关着 → **打开** | turn_off / turn_on |
| 空调 | 关着 → **打开**；其余 → **关掉** | turn_on / turn_off |
| 洗衣机 / 烘干机 / 净水器 / 传感器 | 无 | — |
| 场景 / 脚本 | 在场景行，不出卡片 | activate（脚本新增 `turn_on`，§4.4） |

条件：设备「允许控制」+ 角色达到 `minRole` + 主实体在线 + HA 连着。服务端每次照旧重新校验。

## 4. 模型改动

### 4.1 `smart_home_devices`：一行 = 一台设备

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uuid | 不变；**以后所有引用都用它** |
| `householdId` | uuid | 不变 |
| `haDeviceId` | varchar(64) null | HA 设备注册表的 id；null = 单实体设备（场景、脚本、没有归属设备的 helper） |
| `displayName` | varchar(40) | 中文名，不变 |
| `area` | varchar(20) null | 房间（分组），不变 |
| `icon` | varchar(24) | 图标类型：`vacuum` `curtain` `air_conditioner` `washer` `dryer` `water_purifier` `fridge` `switch` `light` `fan` `sensor` `scene` `other` |
| `primaryEntityId` | varchar(255) | 由原 `entityId` 改名；决定状态句和主按钮 |
| `primaryDomain` | varchar(32) | 由原 `domain` 改名；门锁 / 安防 CHECK 照旧 |
| `secondaryEntityIds` | text[] default '{}' | 至多 4 个（CHECK `cardinality <= 4`）；只读，只进详情 chips |
| `controllable` / `minRole` / `pinnedToToday` / `sortOrder` | — | 不变，含义从「这个实体」变成「这台设备（的主实体）」 |
| `mergeState` | varchar(16) | `legacy`（迁移前的旧行，待归并）/ `ok`；§5 用 |

唯一约束：`(householdId, haDeviceId)`（haDeviceId 非空时）、`(householdId, primaryEntityId)`。
一个实体只能出现在一台设备里（主或次），服务端校验；HA 能连时，主 / 次实体必须属于同一个 `haDeviceId`。

**默认值**（目录里「加进来」时服务端算好，管理员可改）：

- 主实体 = 该设备第一个可控实体（`SMART_HOME_CONTROLLABLE_DOMAINS`，按 vacuum → cover → climate → switch 的顺序）；没有则第一个没有 `entity_category`、也不带米家「* 」前缀的传感器。
- 次要实体 = 除主实体外，前 4 个非诊断 / 非配置传感器（沿用现在目录的 `isPrimarySmartHomeEntity` 规则与排序）。
- 图标类型 = 主实体 domain 推出（vacuum → 扫地机，cover → 窗帘，climate → 空调）；传感器类按设备名 / 型号关键词（洗衣 / 烘干 / 净水 / 冰箱）推，推不出为 `other`。
- 中文名 = HA 设备的 `name_by_user || name`；房间 = HA 设备的区域名。

### 4.2 设备引用：`{ deviceId, entityId }`

E3 / E4 以及 E5 里凡是指向「某台设备的某个实体」的地方，统一换成：

```ts
export const smartHomeEntityRef = z.object({
  deviceId: uuid,              // smart_home_devices.id
  entityId: smartHomeEntityId, // 必须是这台设备的主实体或次要实体
});
```

| 用处 | 现在 | 改为 | 额外约束 |
| --- | --- | --- | --- |
| E3 联动规则（`smart_home_webhook_settings.rules` jsonb） | `washerEntityId` `dryerEntityId` `vacuum.entityId` `filter.entityId` | `washer` `dryer` `vacuum.trigger` `filter.trigger`，均为 `smartHomeEntityRef \| null` | 触发实体可以是次要实体（洗衣机的「运行状态」、净水器的「滤芯寿命」） |
| E4 联动（`smart_home_links`） | `targetEntityId` | 加 `targetDeviceId uuid FK → smart_home_devices ON DELETE RESTRICT`，`targetEntityId` 保留 | 目标实体**必须是主实体**（只有主实体能控） |
| E5 今天页设备卡 | （未实现） | `pinnedToToday` 的设备，按设备 id 出 | — |
| E5 留意规则 | （未实现，`today-attention.rules.ts` 只有占位注释） | `AttentionItem.entity` 指向设备 id，文案用设备中文名；阈值取 E3 规则里的 ref | — |

## 5. 老数据迁移

### 5.1 为什么不能是一个纯 SQL 迁移

现在的白名单行只存了 `entityId`，**没有 HA 的 device_id**。实体属于哪台设备只有 HA 的设备 / 实体注册表知道（E1 修目录时走 WebSocket 读的那三张表）。
TypeORM 迁移里不该去连外部服务，HA 也可能恰好连不上。所以分两步：

| 步 | 在哪 | 做什么 |
| --- | --- | --- |
| ① 表结构迁移 | TypeORM 迁移（离线、可回退） | 加列、改名；旧行 `mergeState = 'legacy'`、`haDeviceId = null`、`primaryEntityId = 原 entityId`、`icon` 按 domain 推；links 加 `targetDeviceId` 并按 `targetEntityId` 回填（此刻一行对一行，必然对得上）；rules jsonb 同理改成 ref；commands 加 `deviceId` 回填 |
| ② 归并 | API 运行时，`SmartHomeMergeService` | 某家庭有 `legacy` 行且 HA 连得上时跑一次（启动时 + live 服务连上 HA 时各检查一次）；事务里做完、幂等；连不上就等下次，**期间旧行各自作为单实体设备照常显示和控制** |

### 5.2 归并规则

一句话：**只重排，不新增**——归并后的设备只包含 King 原来挑过的实体，不会因为归并多出一个他没审过的可控实体。

1. 按注册表把 `legacy` 行按 `device_id` 分组；注册表里查不到、或没有归属设备的实体，各自保持单实体设备。
2. 每组选**主实体**：可控 domain 且原行「允许控制」的 > 可控 domain > 其他非传感器 > 第一个非诊断传感器；同级取 `sortOrder` 小的。
3. 组里其余行成为**次要实体**，按 `sortOrder` 取前 4；超出的不保留，写进归并结果。
4. 合并后的字段：
   - 名字、房间：取主实体那一行（主实体行没填房间就取组里第一个非空的）；
   - **允许控制、谁能控：只取主实体那一行**，绝不因为别的行更宽松而放宽；
   - 在今天页显示：组里任意一行勾了就勾；排序：取最小。
5. 引用改写：
   - E4 联动的目标实体归并后成了次要实体 → 这条联动**停用**（`enabled = false`）并写进结果，因为只有主实体能控；
   - E3 规则的 ref 跟着实体走到新设备；
   - 审计的 `deviceId` 改指向合并后的设备。
6. 被并掉的行删除；每家写一条家庭动态「智能家居白名单按设备整理：N 项 → M 台」；完整结果存下来，供 `merge-report` 端点和汇报用。

### 5.3 让 King 过目

- 实现提交里带一个只读的 **dry-run CLI**（`node dist/smart-home/merge-cli.js --dry-run`），输入就是当前白名单 + HA 注册表，输出一张表：原来的每一行 → 归到哪台设备、做主还是做次、哪些被丢弃、哪些联动会被停用。
- 升级演示栈**之前**先在演示栈上跑 dry-run，结果贴进那一轮汇报，King 点头再升级；升级后 `merge-report` 应与 dry-run 一致。
- 本轮我试过只读查一下演示栈里现在的白名单来做预演，被权限拦下（生产库只读查询），**没有**绕开。按进度记录已知：E2 部署时 King 已挑 G30 U（扫地机）和空调插座两台，截至 E4 部署都还没开放控制、没配 webhook 规则、没建联动——所以真实的迁移量很可能只有十行以内的实体归并，E3 / E4 的引用改写大概率是空操作。**越早做越省事**：King 开始配联动之后，要改写的引用会变多。
