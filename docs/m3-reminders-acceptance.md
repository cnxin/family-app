# M3-D 可配置提醒验收

> 验收日期：2026-07-29
> 状态：通过，跨模块提醒与幂等投递契约冻结

## 验收结论

M3-D 已形成菜单、任务发生日、家庭事件和投票共用的定时提醒闭环。家庭成员可以在移动与桌面 Web 中选择原事项、精确日期时间和多个接收人，并编辑或取消尚未发送的提醒。首页展示近期提醒，独立提醒中心保留待提醒、已发送与已取消状态；到期后每位接收成员只收到一条可跳回原事项的站内通知。

## 数据约定

1. `reminders` 只保存家庭归属、来源模块与 ID、可选任务发生日、精确 `remindAt`、创建者和状态，不复制来源标题、内容或业务状态。
2. `sourceModule` 当前限制为 `menu/task/calendar/poll`。任务必须同时保存 `occurrenceDate`；其他来源禁止保存发生日。
3. `reminder_recipients` 保存接收成员、投递时间和生成的通知 ID，并以提醒与成员建立唯一约束。
4. 提醒状态为 `scheduled/sent/cancelled`。手动取消记录 `manual`；来源失效自动取消记录 `source_unavailable`。
5. 创建和编辑只接受未来时刻，接收人必须是当前家庭的正式成员，单条提醒支持 1 至 20 位且不允许重复。
6. 已发送提醒不可修改或取消；已取消提醒保持历史记录，不重新启用。列表最多返回当前家庭按提醒时间排序的 100 条记录。
7. 到期通知使用 `module=reminder`、`type=reminder_due`，通知来源 ID 指向提醒本身，目标路径由原事项实时解析。

## 调度与一致性

- API 内置调度器默认每 15 秒扫描一次，每批处理最多 25 条；测试可通过 `REMINDER_POLL_INTERVAL_MS` 缩短间隔。
- 同一进程避免重叠扫描；数据库事务使用悲观写锁和 `FOR UPDATE SKIP LOCKED`，多个 API 实例不会领取同一批提醒。
- 投递前重新检查来源：菜单必须开放且仍有有效菜品，任务必须仍发生且为待办，投票必须开放且未过截止时间，家庭事件必须仍存在。
- 每个尚未投递的接收人生成一条通知，再写回 `notificationId` 与 `deliveredAt`；全部完成后才把提醒标记为 `sent`。
- 来源已经结束、停用、归档或删除时不发送通知，而是把提醒标记为 `cancelled`。

## 权限约定

- 所有正式家庭成员都可为当前家庭的有效事项设置提醒，并选择一个或多个同家庭接收人。
- 创建者或 `owner/admin` 可以编辑时间、整体替换接收人或取消待发送提醒。
- 普通成员不能管理他人创建的提醒；跨家庭来源、接收人和提醒按不存在处理。
- 每位成员仍只能在通知中心读取和标记自己的投递通知。

## 接口契约

| 接口 | 作用 |
| --- | --- |
| `GET /reminder-sources?start=YYYY-MM-DD&end=YYYY-MM-DD` | 聚合范围内可提醒的菜单、任务、家庭事件和开放投票 |
| `GET /reminders?status=scheduled\|sent\|cancelled\|all` | 读取当前家庭的提醒与实时来源摘要 |
| `POST /reminders` | 为有效来源设置未来提醒和一组接收成员 |
| `PATCH /reminders/:id` | 创建者或家庭管理员修改待发送提醒的时间或接收人 |
| `DELETE /reminders/:id` | 取消待发送提醒并保留历史状态 |

## 前端约定

- 移动底栏继续保持 6 个高频入口，提醒中心从首页、来源快捷按钮或桌面侧栏进入。
- 提醒中心提供待提醒、已发送、已取消和全部视图；表单按菜单、任务、日程和投票筛选来源。
- 首页最多展示近期 3 条待发送提醒；通知中心使用独立提醒图标和来源分类。
- 菜单餐次、任务卡、日历条目和开放投票均提供鼠标可点的提醒入口，不依赖快捷键。

## 后续边界

- 当前只投递站内通知，不包含 iOS/Android 系统推送、邮件、短信或消息平台；增加渠道时继续复用同一提醒和接收人记录。
- 当前不提供“每次周期任务自动提前多久”的批量规则；任务提醒绑定明确发生日，避免无限预生成提醒。
- 调度器当前随 API 运行。规模或外部渠道增加后可以拆为独立 worker，但仍使用相同数据库领取和幂等契约。
- 提醒时间保存为绝对时刻；增加跨时区家庭前需要补充按家庭时区解释本地时间和夏令时的服务端规则。
